# What a judge should hear (fresh-eyes note, written 15:12 on demo day)

1. What we submitted is sound: the 5 submitted tasks pass the validator with 0 errors and the selfcheck (gold 1.0, untouched 0.0, existing suite green, corrupted gold caught). Our LLM factory adds a rule-to-test fairness gate on top; none of its "hard" candidates passed that gate in time, so none were submitted.
2. Honest headline: Haiku 5.5 (terminus-2) solved everything we benchmarked, 21 of 21 attempts across 7 tasks (re-counted from jobs/*/result.json). We did not stump it, and we are not claiming we did.
3. Why, and it is what the research predicts (teammate brief HaikuSolver.md): on detailed specs the small-model gap nearly vanishes (Haiku 4.5 39.5% vs Sonnet 4.5 43.6% on SWE-Bench Pro), while on short behaviour-only specs where the agent must discover where to change code it is total (Haiku 4.5 0% on DeepSWE). Our instructions were complete specifications with worked examples: an implementation plan plus a self-test oracle. Haiku writes it in one pass and loops on the examples until green.
4. The designs that looked genuinely hard (dependent defaults, response-file completion, atomic output) couple a new feature to 4-6 existing click subsystems. Each one contained at least one sentence that contradicts real click 8.5.1 (prompt callbacks firing twice, Abort/Exit handling in main(), type conversion of falsey values, IntEnum renumbering).
5. Our gates plus an independent Codex reviewer rejected about 20 such designs. We chose to ship zero "hard" tasks over one unfair task. That refusal is the result we are proudest of.
6. Finding: we looked for difficulty in the wrong place. We made the contract longer and more coupled, which (a) kept handing over the plan and (b) multiplied false claims about the baseline. The research says difficulty comes from discovery, parallel routes that must all be updated ("one branch shipped" is the main miss in DeepSWE), preservation of existing behaviour, and rules stated in prose with no example to self-check against.
7. So the bottleneck in an AI task factory is not generating tasks, it is verifying claims about the baseline. Today that check was an LLM judge and a human-like reviewer reading prose.
8. Cost of the evidence: about $1 and 5-13 minutes per generated candidate, about 4 minutes per 3-attempt benchmark; every run, rejection and review is logged (runs/, plan/CHAT.md).
9. Still running at demo time, nothing claimed: four lazy_defaults builds from repaired contracts (323/324/424/425). The reviewer found verified contradictions with real click in every one, including 425, whose contract passed design review but whose generated instruction then made a false claim about parameter sources. So at demo time: zero new tasks with a fair package and a measured Haiku failure. Each repair round closed the named defects and the next layer exposed new ones; that is the argument for line 10.
10. Single best next improvement (the v7 prompt set, PROMPTS.md, was wired at 15:14 and its first runs are in flight, so no result is claimed): a SHORT behaviour-only statement, prose rules with at most two trivial examples, the same behaviour required on every route (command/group/chain, main/CliRunner/ctx.invoke), an explicit list of the existing click behaviour the tests rely on, and a cross-family fairness judge. Pair it with an executable baseline: every "as in 8.5.1" sentence ships with a probe run against the untouched repo before gold is written. Calibrate on Haiku k=3; a failure counts only if the trajectory shows it missed a stated rule.
